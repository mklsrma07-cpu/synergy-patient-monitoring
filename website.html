01 — Why this exists

Continuous care needs continuous, structured data

Patients with coma or severe paralysis require continuous observation, but fragmented patient and fluid data makes systematic monitoring difficult.

Problem statement

Our system provides a structured way to record patient data, track fluid balance, and generate alerts, so observation doesn't depend on scattered notes and memory.

Research background

  • Patient monitoring is based on repeated observations rather than a single measurement.
  • Heart rate, oxygen saturation, temperature, and consciousness are the key monitoring parameters.
  • Fluid balance requires systematic recording of intake and output.
  • Immobility and paralysis create additional care considerations.
  • A good system organizes information and supports observation of change over time.

04 — Under the hood

Seven OOP principles, one patient hierarchy

Every concept below is demonstrated inside the same small hierarchy: a base Patient class, and the specific patient types that extend it.

01

Class & object

A class is a blueprint used to create objects — it defines the attributes and methods an object will have. An object is one instance of that blueprint, with its own values.

In our project — a Patient class holds common fields like name, age, heart rate, SpO₂, and temperature. Each real patient is created as its own object with new.
class Patient {
  String name;
  int age;
  double heartRate, spo2, temp;
}

Patient p1 = new Patient();
p1.name = "R. Sharma";
p1.age  = 47;
02

Encapsulation

Encapsulation combines data and methods inside a class and restricts direct access to that data, using private fields with public getters and setters.

In our project — patient information is sensitive and shouldn't be freely modified from anywhere in the program, so a value like heart rate can only change through a validating setter.
private double heartRate;

public void setHeartRate(double hr) {
  if (hr > 0) heartRate = hr;
  // invalid values are rejected,
  // not silently written
}
03

Constructor & inheritance

A constructor shares the class's name, has no return type, and runs automatically on new — it initializes every attribute at once instead of assigning each one by hand.

Inheritance gives us — code reusability, less duplication, better organization, and a clear relationship between patient types that all share the base Patient class.
class ComaPatient extends Patient {
  ComaPatient(String name, int age) {
    this.name = name;
    this.age  = age;
  }
}
04

Method overriding

Overriding happens when a child class provides its own implementation of a method that already exists in the parent — same name, same parameters, same return type.

In our project — different patient types need different alert behavior even though they share one parent class, so each subtype overrides checkAlert() for itself.
class ParalysisPatient extends Patient {
  @Override
  boolean checkAlert() {
    return spo2 < 92;
  }
}
05

Abstraction

Abstraction hides unnecessary implementation detail and shows only the essential functionality — like using an ATM without knowing the internal banking process.

In our project — we know an alert should perform a checking operation, but the exact implementation differs by alert type, so an abstract class defines the common structure.
abstract class AlertSystem {
  abstract boolean checkAlert();
  // each concrete alert decides
  // its own checking logic
}
06

Exception handling

Exception handling deals with unexpected or invalid situations without crashing the whole program — like negative age, negative fluid values, or an invalid patient type.

Result — a system that's more robust, safer, more user-friendly, and far less likely to crash on incorrect input.
try {
  if (intake < 0)
    throw new IllegalArgumentException(
      "Fluid intake cannot be negative");
} catch (IllegalArgumentException e) {
  showError(e.getMessage());
}
07 — featured

Polymorphism & reusability

Polymorphism means "many forms." It lets the same reference or method call work with different types of objects — our monitoring system can work with a general Patient reference without needing separate code for every patient type. That makes the system flexible, extensible, reusable, and easier to maintain.

Reusability — writing code once and using it many times. If we later add another type, such as PostSurgeryPatient, we extend the existing Patient class instead of building everything from scratch.
Patient current = new_patient_of_any_type();

// same call, different behavior —
// resolved by the object's actual type
if (current.checkAlert()) {
  raisePrototypeAlert(current);
}

// adding a new type later:
class PostSurgeryPatient extends Patient {
  @Override
  boolean checkAlert() { return temp > 38.5; }
}
